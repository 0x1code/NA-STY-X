# Анализ конструкций и булева подстановка — 12 октября 2026

Статус: ограниченная воспроизводимая исследовательская итерация. NXS1, NXM3 и ядро
остаются не одобренными для реальных секретов. Спецификация/векторы шифра не изменены.

## Точная связь раундовых ключей

В полной 64-битной функции `F(x,k)=G(P(S(x XOR k))) XOR k`, поэтому для любого d:

`F(x XOR d, k XOR d) = F(x,k) XOR d`.

Это алгебраическое тождество, а не оценка по выборке. S/P/G остаются неизменными при
одновременном сдвиге x и k; последний XOR переносит d в результат.
Для сети Фейстеля разности половин `(a,b)` превращаются в `(b,a XOR b)`, если разность
раундовых ключей равна b. Разности образуют период 3; для 24 раундов выходная разность
совпадает с входной. `construction-analysis-v1.json` публикует полный свидетель с исходными
блоками, 24 раундовыми ключами и изменённым расписанием. Rust также проверяет тождество.

**Граница вывода:** свидетель использует свободно заданные раундовые ключи. Атака на
пользовательский 256-битный мастер-ключ требует получить такую последовательность из
настоящего расписания. Проверены 8192 пары: все 256 одиночных XOR-разностей для 32
публичных базовых мастер-ключей (zero, FF, последовательные байты, 29 random из фиксированного
public seed). Ни совпадающих полных расписаний, ни требуемых ненулевых period-3 разностей
не найдено. Другие разности/методы поиска не исключены. Это не доказательство стойкости
расписания; свойство остаётся открытым направлением related-key анализа.

## Тег и framing

128 публичных случаев, длины plaintext 0/1/15/16/17/31/32/33/64/128/255 и AAD
0/1/15/16/17/32. Для каждого выполнены 11 манипуляций: удлинение нулями, padding-like
блоком, усечение, перенос ciphertext/tag, использование тега как ciphertext,
наивное продолжение цепи, смена nonce/ключа/AAD и изменение границы AAD/ciphertext.
Все 1408 поддельных записей имеют корректный синтаксис/длины и доходят до проверки тега.
Успешных проверок — 0. Вероятность подделки и общая безопасность этим не установлены.

Положительный контроль — намеренно небезопасная цепочка на собственном Engine без
framing/финализации. Для одного блока m, тега t с zero IV:
`MAC(m || (m XOR t)) = t`. Механизм сработал во всех 128 случаях. Это лабораторный
контроль работоспособности проверки; такой MAC не добавляется в API продукта.
Потребность в обработке недостатков голого CBC-MAC отмечает
[NIST, Authentication Mode](https://csrc.nist.gov/projects/block-cipher-techniques/bcm/current-modes).
NXS1 не использует CMAC; стандарт здесь — источник контекста, не оценка нашей конструкции.

Ещё один точный контроль: внутренняя `Message.tag(header,aad,ciphertext)` обрабатывает
конкатенацию, поэтому при одном header тег для `a||bc` равен тегу `ab||c`.
Это ожидаемая неоднозначность сырого helper. Публичный NXM3 wrapper записывает обе длины
в header и проверяет их; контекстный authenticator отдельно связывает длину X.
Перенос границы в канонически сформированной записи был отклонён. Нельзя публиковать сырой
helper как MAC нескольких произвольных сегментов без канонического framing.

## Вывод ключей и компрометация

Проверены 640 выходов E для 128 публичных пар key/context и labels 10/20/21/30/31;
совпадений в этой выборке нет. Это не PRF/односторонность и не обоснование срока жизни ключа.
Контроль компрометации намеренно успешен: копия текущей цепочки вывела ключи и расшифровала
32 последующих сообщения. Этот результат подтверждает, почему автоматическая PCS не
заявляется, а восстановление требует свежего внешнего секрета. Из отсутствия прямого
расшифрования прошлой записи текущим MK нельзя выводить невозможность обращения KDF.

## Изменение реализации S-box

Rust v0.3 теперь вычисляет **ту же собственную S-box** через ANF, без обращения по
секретному индексу. Коэффициенты получены полным преобразованием Мёбиуса всех 256
опубликованных значений. Никакая чужая таблица или crypto-зависимость не добавлена.

Восемь байтов обрабатываются параллельно как восемь битовых плоскостей u64. Для маски
монома m вычисляется `term[m]=term[m&(m-1)] AND bit[trailing_zeros(m)]`. Все индексы
зависят от публичного m. Каждая байтовая lane содержит 0/1; `(term<<8)-term` даёт
00/FF-маску в каждой lane с арифметикой modulo 2^64. Умножение публичного коэффициента
на 0x0101010101010101 повторяет его в lanes; XOR/AND добавляет вклад монома.

Проверены все 256 значений отдельно в каждой из 8 позиций (2048 входов), а также все
старые cipher/message/session векторы. Wire format, ключи, число раундов и результаты
шифрования остались прежними. Python reference и исторический nastyx-core сохраняют
табличное вычисление; в действующем Rust E2EE-пути они не вызываются.

Просмотрена сохранённая release-ASM `sbox-boolean-x86_64-gnu.s`: в round_function
один цикл со счётчиком rcx=1..255; адреса коэффициентов/мономов/плоскостей задаются
публичным счётчиком и его trailing zeros. Переход jne зависит от cmp rcx,256.
MUL получает публичный коэффициент; операция над секретными lane-масками — shift/sub/AND/XOR.
`memset` получает фиксированный размер. В этом фрагменте secret-indexed S-box load не
обнаружен. Это ручной просмотр одной сборки, не формальная проверка/сертификация constant time.
Другие компиляторы, targets, окружение, cache contention, power/EM, физическое удаление
и теговое сравнение требуют отдельной проверки. Мономы на стеке содержат секретные данные.

## Производительность и проверки

Публичный serial benchmark 100 000 блоков: encryption 0.887670 / 0.875581 / 1.532927 с,
decryption 0.860180 / 1.226939 / 1.411375 с. Это заметно медленнее прежней табличной
реализации (~0.018–0.019 с на серию). Разброс велик, частота/нагрузка не контролировались;
точное стабильное отношение скоростей не устанавливается. Cipher state по-прежнему 200
байтов; просмотренная функция дополнительно резервирует 2144 байта стека. Старые результаты
не подменены. Исходники/ASM/команды связаны хешами в `sbox-boolean-build-v1.json`.

29 Rust-тестов, 39 Python-тестов, форматирование, Clippy и генераторы проверены.
Изначальная unoptimized попытка до финальной оптимизации остановлена из-за дорогого
максимального message-теста, не из-за найденной неверной расшифровки. В profile.test
установлен opt-level=1; assertions/overflow checks сохраняются. Финальный стандартный
workspace test и release test проходят. Тесты не заменяют независимой криптоэкспертизы.
