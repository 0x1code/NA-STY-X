# NXS1 — E2EE-сеанс связанных устройств

**Ревизия:** 0.4.0-alpha, 12 октября 2026. **Исследовательский прототип.**
Рабочий обмен пакетами не подтверждает стойкость собственного шифра, MAC или KDF.
Для защиты реальных секретов эта версия не одобрена.

## Граница доверия

Сервер получает только handshake и зашифрованные записи. Он может менять, повторять,
переставлять, задерживать и удалять пакеты. Клиенты проверяют записи до выдачи текста.
Доступность не гарантируется. ID устройств/сеанса, направление, номера, размеры и время
доступны серверу.

Связывание требует **случайного одноразового секрета 32 байта** через отдельный доверенный
канал, вместе с двумя различными ID устройств по 16 байт. Пароль, PIN и публичный ключ
из тестов не подходят. Rust получает энтропию от вызывающей программы; demo использует
`secrets.token_bytes` системного RNG. Pairing потребляется, но повторное создание объекта
с прежним секретом запрещено контрактом вызывающей программы. Это не асимметричное
согласование и не безопасный первый контакт через единственный недоверенный сервер.

После handshake пользователи сверяют **полный 16-байтовый код** через доверенный канал.
Код подтверждает владение секретом/соответствие транскрипта, а не юридическую личность
владельца ID. Нельзя доверять подтверждению только от сервера. Неподтверждённый сеанс
не предоставляет `seal/open`.

## Строительные функции

`A(K,X)` — `nastyx-message::authentication_code`: MAC-цепь v0.3 с независимой финализацией,
заголовком `D('H',0,0)||BE32(len(X))`, контекстом X и пустым ciphertext.
D определена в `MESSAGE_SPEC_V0_3.md`.
`C(K,L,X) = A(K, ASCII("NXS1") || byte(L) || X)`.
`E(K,L,X) = C(K,L,0x00||X) || C(K,L,0x01||X)` — 32 байта расширения.

Все внутренние контексты фиксированы/ограничены. Код не использует AES, ChaCha, HMAC,
DH, Signal или готовую KDF. Разделение ролей, цепочки и подтверждение ключей — общие
архитектурные приёмы, без заявлений об изобретении новых математических принципов.
Односторонность/независимость E не доказаны. 32 байта выхода не означают доказанной
256-битной стойкости; теги имеют 128 бит.

## Handshake

A выбирает независимо случайные SID и NA по 16 байт. B выбирает NB той же длины.
`T0 = ID_A || ID_B || SID || NA` (64 байта), `T = T0 || NB` (80 байт).

`H(type,body,K) = ASCII("NXH1") || byte(type) || body ||
C(K,type,ASCII("NXH1")||byte(type)||body)`.

| Запись | Body | Ключ проверки | Длина |
|---|---|---|---|
| Offer, type=1 | T0 | одноразовый секрет P | 85 |
| Reply, type=2 | T | P | 101 |
| Confirm, type=3 | T | `R=E(P,10,T)` | 101 |

B проверяет точный размер/тип/тег/оба ID. A проверяет reply и байтовое соответствие T0
своему запросу. B проверяет confirm и соответствие полного T своему ответу. Объекты
ожидания потребляются даже при ошибке; повтор требует нового связывания.
Код сверки `C(R,11,T)` одинаков для обеих сторон. Направления: A→B=0, B→A=1.
Начальные цепочки: `E(R,20,T)` и `E(R,21,T)`. После их создания P/R отсутствуют
в логическом активном состоянии. ACK доставки confirm не предусмотрен: при потере B
не активен; клиенты повторяют связывание, без отката ключей или fallback.

## Записи и цепочки

Для цепочки K, направления d, номера n:
`X = byte(d)||BE64(n)`; `MK_n = E(K,30,X)`; `K_next = E(K,31,X)`.
MK потребляется один раз. NXM3-запись использует фиксированный нулевой nonce 12 байт:
безопасность зависит от уникальности MK. Rust OneTimeSealer не Clone/Copy и потребляет
себя. Создание второго sealer с тем же ключом нарушает контракт. Для длительного ключа
нужно прежнее API Sender с persistent nonce-реестром.

Внешний заголовок (68 байт) полностью входит в AAD NXM3:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | ASCII NXS1 |
| 4 | 1 | направление 0/1 |
| 5 | 3 | нулевые reserved |
| 8 | 16 | SID |
| 24 | 16 | ID отправителя |
| 40 | 16 | ID получателя |
| 56 | 8 | номер, big-endian |
| 64 | 4 | длина NXM3, big-endian |
| 68 | N | NXM3: zero nonce, ciphertext, тег |

Max plaintext 65 536, max packet 65 648 байт, overhead 112. Номера 0..1 048 575
для каждого направления, затем новый сеанс. Это эксплуатационные лимиты, не доказанные
криптографические квоты. Неизвестный формат/лишние байты отклоняются. Отправитель меняет
цепочку до возврата ciphertext.

Получатель хранит до 64 skipped keys; максимальный разрыв тоже 64. Вывод происходит
на временном состоянии. Цепочка/удаление skipped keys меняются **после проверки тега**.
Поддельный высокий номер не вытесняет корректные записи. Принятая запись не принимается
повторно. Skipped key удаляется после доставки. `discard_skipped()` явно исключает
доставку оставшихся потерянных записей. При полном окне: доставить пропущенные, отбросить
их явно или новый сеанс. Безграничный reorder/loss и надёжная доставка отсутствуют.

## Сбои, удаление ключей, восстановление

Состояние **только в памяти**, без записи секретов на диск. Перезапуск требует нового
одноразового P и handshake; старые пакеты не подходят новому сеансу. Нельзя копировать,
сериализовать, восстанавливать VM snapshot, fork или запускать две копии цепочки.
Rust Session не Clone и не экспортирует секреты. Python — reference, не hardened SDK.

Затирание массивов Rust — best effort: оптимизатор, временные копии, swap/дампы могут
сохранить данные. Python не гарантирует стирание памяти. Защищённое долговременное
хранилище ключей/истории, hardware keystore и crash-safe ratchet — отдельный этап.
Demo показывает UTF-8, низкоуровневые Session поддерживают произвольные байты.

**Прямая секретность:** логически прошлые цепочки/MK не сохраняются после доставки.
Skipped keys позволяют прочитать соответствующие недоставленные сообщения. Защита
прошлой переписки от текущего состояния требует односторонности E, стойкости MAC и
фактического удаления P/R/старых ключей. Эти условия пока не подтверждены.

**После компрометации:** текущая цепочка раскрывает последующие ключи направления.
Симметрический шаг не добавляет неизвестную атакующему энтропию. Рабочий путь восстановления:
очистить устройства, закрыть оба старых сеанса, передать новый случайный P через отдельный
доверенный канал и сверить новый код. Передача P по старому скомпрометированному сеансу
не восстанавливает защиту. Автоматическая PCS, асимметричное согласование и quantum security
не реализованы/не заявляются.

## Несколько устройств

Каждая пара имеет свои ID, отдельный свежий P и независимый сеанс. Для нескольких
получателей текст шифруется отдельно для каждой пары. Нельзя делить цепочку/P между парами.
Автоматический каталог, добавление/отзыв по сети, группы и синхронизация истории отсутствуют.
Тесты изоляции пары/закрытия — не готовый multi-device сервис.

## Векторы и демонстрация

`tests/vectors/session-v1.hex`: строки P, ID_A, ID_B, SID, NA, NB, offer, reply,
confirm, код сверки, затем 4 пары plaintext/packet (направления 0,0,1,0). Ключи публичные.
Rust проверяет байтовое совпадение с независимым Python.

`py -3 demos/e2ee_chat.py --interactive`: relay HTTP на случайном loopback-порту и два
клиентских процесса. Доверенный локальный пульт передаёт приглашение через pipes и сверяет
коды, имитируя отдельный доверенный канал; секрет не проходит relay. Пульт видит текст
клиентов, relay — только пакеты. Loopback HTTP не защищает от локального malware и
не является готовым развёртыванием для реальной сети. Отчёт объединяет публичные demo-тексты
клиентов и ciphertext relay; он не является журналом relay и запрещён для настоящей переписки.

## Источники границ свойств и анализ

Требование неизвестной новой энтропии для восстановления после компрометации:
[Double Ratchet, KDF chains](https://signal.org/docs/specifications/doubleratchet/).
Источник используется для терминологии/ограничений; алгоритмы Signal не интегрированы.
Независимый криптоанализ не выполнен. Пакет вопросов: `REVIEW_REQUEST.md`.
Тесты проверяют совместимость/ошибки, не доказывают невозможность криптографической атаки.
