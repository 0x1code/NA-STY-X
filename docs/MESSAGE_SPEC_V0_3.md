# NA&STY-X Message v0.3

**Статус:** работающий исследовательский модуль шифрования и проверки целостности. Это не утверждённый AEAD и не готовый защищённый протокол. Готовые стандартные шифры или MAC-библиотеки не используются; зависимость Rust — только наше ядро v0.3.

Композиция использует общие приёмы: XOR со счётчиковым потоком и цепочку для тега с отдельной финализацией. Эти приёмы не объявляются новым математическим изобретением. Стойкость конкретной композиции и собственного ядра ещё не установлена.

## Ключи и домены

Вход — случайный 32-байтовый мастер-ключ, заранее переданный через доверенный канал. Пароли не подходят. Генерация ключей, согласование ключей и аутентификация личности участников здесь не реализованы. Производный ключ не добавляет энтропии исходному.

Определить блок `D(kind,role,part)` как байты `[78,88,kind,3,role,part]` и десять нулей. `E` — наше ядро v0.3 на 24 раундах.

Для ролей 1 (поток), 2 (цепочка тега), 3 (финализация):

`Krole = E_master(D(75,role,0)) || E_master(D(75,role,1))`.

Это собственная экспериментальная схема разделения ключей, а не стандартный KDF. Разные метки разделяют вызовы; криптографическая независимость ключей требует анализа. Непубличные ключи не выводятся в логи и не сохраняются в nonce-реестр.

## Формат записи

| Смещение | Длина | Значение |
|---:|---:|---|
| 0 | 4 | ASCII `NXM3` |
| 4 | 1 | Версия ядра 3 |
| 5 | 1 | Набор параметров 1: 24 раунда |
| 6 | 2 | Нулевые зарезервированные байты |
| 8 | 12 | Nonce |
| 20 | 4 | Длина внешнего контекста, big-endian |
| 24 | 4 | Длина шифротекста, big-endian |
| 28 | N | Шифротекст |
| 28+N | 16 | Тег |

Контекст не включён в запись: обе стороны передают одинаковые байты в API. Он аутентифицируется вместе с заголовком и шифротекстом. Размер открытого текста <= 1 МиБ, контекста <= 64 КиБ. Принимается ровно одна запись, без хвостовых байтов. Неизвестные версии, наборы и флаги отвергаются, fallback отсутствует.

## Шифрование и тег

Для блока сообщения `j`, начиная с нуля:

`stream[j] = E_K1(nonce || BE32(j))`, `C[j] = P[j] XOR stream[j]`.

Последний неполный блок использует только нужные байты потока. Лимит размера исключает переполнение 32-битного номера блока. Пустое сообщение имеет тег и тоже расходует nonce.

```text
H = E_K2(D(77,0,0))
B = header || context || ciphertext || 0x80 || zero padding to a multiple of 16
for block in B:
    H = E_K2(H XOR block)
T = E_K3(H XOR D(70,0,0))
```

Заголовок задаёт обе длины до данных, чтобы разбиение контекста и шифротекста было однозначным. Дополнение всегда содержит 0x80, включая выровненные данные. Отдельная финализация скрывает внутреннее состояние цепочки; это мотивировка конструкции, а не доказательство защиты от подделки.

Приёмник сначала проверяет формат и размеры, затем весь тег. До успешной проверки дешифрование и выдача открытого текста не выполняются. Неверный ключ, контекст, тег или формат дают `Rejected`. Rust сравнивает все 16 байтов с накоплением XOR, но постоянное время машинного кода не подтверждено. Python использует библиотечное сравнение байтов `compare_digest`, а не сторонний алгоритм MAC.

## Nonce и перезапуск

Производственный API не позволяет передать nonce вручную. Исследовательский Python допускает явный nonce только для тестовых векторов.

Nonce отправителя — четыре нулевых байта и BE64 счётчика. `Sender::initialize` явно создаёт реестр только для нового ключа. `Sender::open` требует существующих корректных метаданных и никогда не создаёт отсутствующее состояние автоматически.

Для ключа выбирается каталог по публичному идентификатору `E_master(D(73,0,0))`. В одном общем реестре атомарное создание файла `counter.used` резервирует значение **до шифрования**. Файл синхронизируется; на Unix синхронизируется и каталог. Другие отправители пропускают уже созданные файлы. Ошибка записи прекращает операцию без возврата шифротекста; созданный маркер всё равно считается использованным. Повторное открытие обнаруживает все оставшиеся маркеры. Лимит — 1 048 576 записей на ключ; это операционный предел, а не доказанная безопасная квота.

Один ключ должен использовать один реестр на локальной файловой системе с корректной атомарной семантикой create-new. Другой каталог, откат резервной копии, удаление маркеров или повторная инициализация старого ключа могут повторить nonce. Это невозможно обнаружить одним локальным счётчиком без дополнительного доверенного состояния. После потери/сомнения в состоянии нужен новый ключ. На Windows файловая синхронизация не доказывает сохранность метаданных каталога после отключения питания; такой сбой не входит в подтверждённую гарантию. Облачные/сетевые синхронизируемые каталоги не являются поддерживаемым реестром.

## Что проверено и что осталось

Rust и Python совпадают на 10 векторах длиной 0..1024 байта, включая границы блоков. Тестируются изменения каждого бита небольшой записи, изменение каждого байта всех Python-векторов, неверные ключи/контексты, усечение, расширение, максимальные размеры, ошибки хранилища и исчерпание, повторное открытие, четыре параллельных отправителя и незавершённое резервирование nonce.

Не выполнены независимый криптоанализ тега/KDF, формальная оценка подделок и срока жизни ключа, гарантия постоянного времени и очистки памяти, устойчивость к откату файловой системы. Получатель не хранит состояние повторов: ранее корректная запись снова принимается. Сессионный протокол, разделение направлений, смена ключей и прямая секретность — следующий этап.

## Запуск демонстрации

```powershell
cargo run -p nastyx-message --example research_roundtrip
```

Демонстрация использует явно публичный тестовый ключ и фиксированный текст. Её ключ запрещено использовать для реальных данных. Для интеграции доступны Rust API `Sender::{initialize,open,seal}` и `Receiver::{new,open}`; пример не является инструкцией к production-развёртыванию.
